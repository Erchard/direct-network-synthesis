# Як відкрити канал між агентами

Цей документ пояснює, що може зробити оператор із доступом до Інтернету, щоб
з'єднати зовнішніх агентів із дослідницьким процесом DNS.

## Важливе обмеження

Поточний Codex-сеанс не є публічним сервером і не слухає вхідні HTTP, WebSocket
або A2A-з'єднання. Тому недостатньо просто відкрити порт, створити URL чи
опублікувати Agent Card. Для прямого автоматичного обміну потрібен окремий
конектор, встановлений у середовище агента, або зовнішній relay, який має право
передавати повідомлення в цей сеанс.

Не передавайте зовнішньому агенту ключі GitHub, секрети Codex, cookies,
облікові дані або доступ до робочої теки. Публічний канал має передавати лише
опис задачі, посилання на відкриті файли та reviewable результат.

## Три реальні рівні підключення

### 1. Ручний relay: доступно вже зараз

1. Опублікувати або знайти зовнішнього агента в дозволеному каналі.
2. Передати йому одну bounded task, наприклад GitHub issue OAC-03.
3. Принести його відповідь, diff або посилання на PR у цей чат.
4. Я перевірю результат за правилами репозиторію.

Це не повністю автоматичний канал, але він уже працює і не потребує надання
цьому чату мережевих прав.

### 2. Публічний discovery endpoint: наступний технічний крок

Оператор може розмістити на власному домені протокол-нейтральну або A2A-сумісну
картку можливостей, наприклад у `/.well-known/agent-card.json`, і вказати в ній:

- що DNS шукає аудити, reproductions і prior-art перевірки;
- адресу canonical GitHub repository та конкретних issues;
- дозволені типи повідомлень;
- вимогу працювати через fork/branch і PR;
- що endpoint не приймає секрети, платежі чи команди на виконання коду.

Це робить проєкт видимим для інших агентів, але саме по собі не підключає їх до
цього Codex-сеансу. Endpoint повинен мати HTTPS, журналювання, rate limit,
контроль розміру повідомлення і documented shutdown path.

### 3. Прямий автоматичний relay: потрібна інтеграція

Для справжнього agent-to-agent обміну потрібен окремий процес на машині або
сервері оператора:

`external agent -> relay -> approved connector -> Codex task`

Relay має фільтрувати повідомлення за allowlist, зберігати лише потрібний
журнал і вимагати підтвердження перед будь-якою дією, що змінює репозиторій.
Публічний A2A або Agentverse endpoint може бути транспортом для зовнішнього
агента, але не є автоматичним мостом до цього чату без відповідного connector
або plugin у середовищі Codex.

## Рекомендований перший запуск

1. Взяти OAC-03 як першу задачу: вона працює лише з опублікованими файлами і не
   потребує benchmark execution.
2. Передати зовнішньому агенту цей issue та
   `docs/outreach/research-packets.md`.
3. Отримати звіт або PR через ручний relay.
4. Після першого успішного проходження оцінити, чи потрібна автоматизація.
5. Лише потім створювати статичну A2A-картку або registry listing.

## Мінімальний формат повідомлення

```json
{
  "task_id": "OAC-03",
  "repository": "https://github.com/Erchard/direct-network-synthesis",
  "issue": "https://github.com/Erchard/direct-network-synthesis/issues/3",
  "allowed_inputs": [
    "docs/results/dns05_failure_scaling_audit.json",
    "docs/research-log.md",
    "docs/dns05-failure-scaling-audit-protocol.md"
  ],
  "forbidden": [
    "secrets",
    "private_data",
    "test_partitions",
    "arbitrary_code_execution"
  ],
  "requested_output": "reviewable audit report or pull request"
}
```

## Безпекова межа

Перший канал має бути read-only щодо репозиторію. Зовнішній агент не повинен
отримувати merge access, write token, доступ до локальної теки або дозвіл
запускати довільні команди. Будь-який майбутній connector потрібно спочатку
перевірити на synthetic messages і окремому тестовому endpoint.
